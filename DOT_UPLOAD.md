# CloudHandset file upload

Codex **0.1.5**, Dot **0.2.6**, Muse setup kit **0.1.4**, and Grok Bot **0.1.3** include the existing upload helper. These versions are published under **plugins-2026.11.17**; see [release status](RELEASE_STATUS.md).

Dot's host may provide an original attachment or a derived file. A normal attachment download and the file exposed to the agent can differ; no universal original-byte path is certified. If the supplied size/SHA cannot be reproduced from the actual input, stop before acquiring control or uploading. Do not relax integrity checks, manually reconstruct encoding, or search unrelated histories.

Use this workflow for a user-requested file transfer. It reuses CloudHandset's existing upload, integrity check and Android phone writer. Maximum file size is 30 MiB. Validate the supplied file before acquiring the selected phone's exclusive `session_id`; a file-only preflight needs no phone control.

1. In the host execution environment, run `python3 scripts/upload_file.py inspect /absolute/path/to/file`. Use the actual attachment/local file. The result contains `name`, `size`, and `sha256`; no file bytes enter the model context. If the user supplied an expected size or digest, require an exact match before uploading. Do not manually retype, guess, or repair a long encoded payload. If exact bytes are unavailable or a check fails, report the input problem and request the original attachment; do not search unrelated files, chat transcripts, histories, or account data to reconstruct it.
2. After the file passes preflight, acquire the selected phone through the existing authenticated MCP connection. Then call `device_tool` with `action: "file.upload_begin"`, that `session_id`, a fresh `operation_id`, and the three returned file fields. Save `result.upload_id` and the returned `upload` ticket (including `complete_operation_id`) in private process memory or a temporary file accessible only to the user. Never display or publish `upload_token`. It is a one-use capability for this exact file and control session, valid for at most ten minutes; it cannot list or operate phones. Do not extract OAuth credentials.
3. Run `python3 scripts/upload_file.py send /absolute/path/to/file`, supplying only the returned `upload` ticket object as JSON on **stdin**, not command-line arguments. The helper sends one binary PUT to the fixed CloudHandset host. It checks file size/digest, blocks redirects, never retries, and never uses browser cookies or another client's credentials. Remove any private temporary ticket file afterward.
4. A successful PUT means staging finished and final phone transfer was submitted. If `receipt.result.state` is `running`, call the authenticated `device_tool` with `action: "operation.status"`, `session_id`, and the returned **complete_operation_id** until a terminal state, using bounded polling. Success requires `result.state: "succeeded"` plus the expected `bytes` and returned `path`. Preserve both operation IDs on interruption. A lost PUT response is not permission to repeat PUT or prepare another upload: query the original completion operation; if absent, inspect `file.upload_status` for the same upload and report the unresolved transfer.
5. Supported videos/images request Android media scanning where the device Bridge supports it. Verify visibility in the intended app if the task requires it. A successful transfer does not establish publication. Release control and confirm closed/drained after the task.

To cancel, use authenticated `device_tool`, `action: "file.upload_cancel"`, the original `session_id`/`upload_id` and a new operation ID for the cancellation. Session release, lease expiry, revoked account access and manual pause stop the upload writer. Failed transfers are not automatically replayed.

The transfer uses an independent 4 MiB/s byte budget and continuously sends the original 32 KiB chunks from the server. It does not consume one phone-action quota entry per chunk. Normal phone controls retain their existing limits. Each chunk rechecks account/lease/session access; Bridge permits are checked before every original chunk and final device write.

If the current tools do not expose `file.upload_begin`, refresh the existing connection's tools and reload the updated skill. If the begin response does not include an `upload` ticket, the server or selected Android phone does not support this workflow. Report that specific gap. The older `file.upload_begin/chunk/complete` protocol remains compatible, but do not silently fall back to hundreds of slow tool calls.

The host must be able to read the selected file and run the packaged uploader. A local path is read by the host helper, never by the remote MCP server. If that execution/file capability is unavailable, report it; do not invent file bytes or substitute an arbitrary URL fetch.


## Muse completion checks

Muse uses the unchanged adapter 0.1.2 from setup kit 0.1.4. Run `bin/upload_file.py inspect` against the actual file before acquiring control, then use the wrapper described in [TOOLS.md](muse/TOOLS.md#fast-upload-011). Its `upload` command queries the original completion operation within a bounded budget and separately checks whether the session remains active. A completed transfer does not authorize a next upload after session closure.

Keep session_id, upload_id, complete_operation_id and expected_size for read-only `upload-status` when pending or unknown. Never repeat PUT or start a new upload to resolve uncertainty. Share polling/release budgets as described in [parallel control](PARALLEL_CONTROL.md).
